## 1장. 미션 소개 — "내 상황을 아는 AI 비서"

**① 과제가 요구한 것**
- 일반 ChatGPT는 내 데이터를 모른다 → 내 데이터를 이해하고 맞춤형 답변을 주는 AI 서비스
- 시계열 데이터 분석 → DB 저장 → AI가 그 데이터를 기반으로 대화하는 웹 서비스

**② 우리가 만든 것**
- 시계열 데이터: 업비트 KRW-BTC **일별 종가 400개** (2025-09-03 ~ 2026-10-07)로 시작해, 매일 아침 알림 실행 때 빠진 날짜를 업비트에서 자동 추가 (그래서 지금 화면에는 401개 이상)
- DB: Firestore `data` 컬렉션
- AI 대화: `POST /api/chat` — 질문마다 최신 요약을 시스템 프롬프트에 넣어 답변
- 보여 줄 곳: 배포 사이트 채팅창, README 1장

**③ 이렇게 말하기**
> "ChatGPT에 '요즘 비트코인 어때?'라고 물으면 제 데이터를 모르니까 일반론만 말하거나 숫자를 지어냅니다. 그래서 제가 저장한 400일 시세를 서버가 요약해서 AI에게 매번 넣어 주고, AI는 그 요약 안의 숫자만 근거로 답하게 했습니다."

**④ 깊게 물으면**
- **Q. 왜 비트코인 데이터를 골랐나요?**
  A. 변동이 커서 "추세가 어때?", "언제 크게 떨어졌어?" 같은 질문거리가 많고, 키 없이 받을 수 있는 공개 API라 재현이 쉽습니다. 그리고 제가 직접 거래해 본 경험이 있어서, 팔 타이밍을 놓치는 문제를 풀고 싶었습니다.
- **Q. "내 상황을 안다"는 게 정확히 뭔가요?**
  A. AI가 일반 지식이 아니라 **제 DB에 저장된 숫자**(평균 1억 2,013만 원, 최고 1억 7,801만 원 등)를 근거로 답한다는 뜻입니다. 데이터를 수정하면 다음 답변이 바로 바뀝니다.

## 2장. 최종 결과물 — 4가지 기능

| 과제 기능 | 입력 → 출력 (과제 문구) | 우리 구현 | 보여 줄 곳 |
|---|---|---|---|
| 1. 데이터 기반 AI 채팅 | 자연어 질문 → 요약을 반영한 답변 + 로딩 표시 | 채팅창, 보내는 동안 점 3개(…) 애니메이션 + 보내기 버튼 비활성화 | 사이트 채팅 |
| 2. 데이터 관리(CRUD) | (date, value, memo) 추가/수정/삭제 → 목록 갱신 | 오른쪽 "데이터 관리" 표, 추가 폼, 행마다 수정·삭제 | 사이트 데이터 관리 |
| 3. 대화 기록 | 저장·목록·불러오기 → 목록과 메시지 재표시 | 왼쪽 "대화 기록", 누르면 이전 대화 그대로 다시 표시 | 사이트 대화 기록 |
| 4. 배포·문서화 | 배포 URL 접속 → 서비스 + Swagger + README | Vercel·Render 배포, `/docs`, README | 주소 3개 |

**④ 깊게 물으면**
- **Q. 로딩 표시는 어떻게 했나요?**
  A. 질문을 보내면 답이 오기 전까지 말풍선 자리에 점 3개가 깜빡이는 표시를 띄우고, 보내기 버튼을 비활성화해 중복 전송을 막았습니다. 답이 오거나 오류가 나면 표시를 지우고 버튼을 다시 켭니다. (`frontend/app.js`의 `showTyping()`, `sendMessage()`)
- **Q. 데이터를 수정하면 화면 어디가 바뀌나요?**
  A. 목록, 요약 카드, 그래프, 위험 단계가 한 번에 다시 불러와집니다(`refreshAll`). 서버 쪽에서도 요약 캐시를 지워서 AI의 다음 답변에 바로 반영됩니다.

## 3장. 과제 목표 — "스스로 설명할 수 있어야 한다" (가장 많이 물어보는 부분)

### 3-1. 시계열 데이터를 분석해 요약을 만들고 활용하는 흐름

**③ 이렇게 말하기**
> "흐름은 4단계입니다. 업비트 API에서 일별 종가를 받아 → 빠진 날짜·0 이하 값을 점검하고 → Firestore에 저장한 뒤 → 서버의 `build_summary()`가 기간·개수·평균·최고·최저·추세를 계산합니다. 이 요약을 ① AI 시스템 프롬프트, ② 화면의 요약 카드, ③ 위험 단계 계산에 함께 씁니다."

**요약에 들어가는 것 (GET /api/data/summary)**
- 기간 `2025-09-03 ~ 2026-10-07`, 개수 `400`
- 최근 값 1억 1,344만 9천 원, 평균 1억 2,013만 원
- 최고 1억 7,801만 원(2025-10-08), 최저 8,912만 원(2026-08-14)
- 기간 변화 −26.76%, 30일 변화 +5.32%, 일간 변동성 2.02%
- 상승일 비율 48.6%, 최대 낙폭 −49.94% (2025-10-08 → 2026-08-14)
- 이번 달 평균과 월평균 비교(−3.76%), 가장 높은 달 2025-10, 가장 낮은 달 2026-07
- 최근 14일 값, 월별 평균·최고·최저, 급등·급락 메모
- **추세**: "상승 (최근 30일 평균이 직전 30일 대비 +9.6%)"

**④ 깊게 물으면**
- **Q. 추세(상승/하락/보합)는 어떤 기준으로 정했나요?**
  A. 최근 30일 평균을 그 직전 30일 평균과 비교해서 **+3% 이상이면 상승, −3% 이하면 하락, 그 사이는 보합**입니다. 하루하루 출렁임에 흔들리지 않게 30일 평균끼리 비교했습니다.
- **Q. 일간 변동성은 뭔가요?**
  A. 하루 수익률(전날 대비 변화율)의 표준편차입니다. 2.02%면 하루에 보통 ±2% 정도 움직인다는 뜻입니다.
- **Q. 최대 낙폭(MDD)은 어떻게 계산하나요?**
  A. 날짜 순으로 가며 그때까지의 최고가를 기억하고, 그 최고가 대비 가장 크게 떨어진 비율을 찾습니다. 우리 데이터는 2025-10-08 고점에서 2026-08-14 저점까지 −49.94%입니다.
- **Q. 급등·급락 메모는 누가 썼나요?**
  A. 데이터를 받을 때 하루 ±5% 이상 움직인 날에 "일간 −13.9% 급락"처럼 자동으로 적었습니다. AI가 "급락했던 날 알려줘"에 답할 수 있게 하려고요.
- **Q. 데이터 정제는 했나요?**
  A. 받는 스크립트(`backend/scripts/seed_upbit.py`)가 빠진 날짜 수와 0 이하 값 수를 출력해 점검하고, 같은 날짜가 두 번 저장되지 않게 이미 있는 날짜는 건너뜁니다.
- **Q. 요약을 매번 다시 계산하면 느리지 않나요?**
  A. 한 번 계산한 요약을 메모리에 저장(캐시)해 두고, 데이터가 추가·수정·삭제될 때만 지워서 다시 계산합니다.

### 3-2. FastAPI를 라우터/서비스로 나눈 기준

**③ 이렇게 말하기**
> "라우터는 식당의 **창구**, 서비스는 **주방**이라고 생각했습니다. 라우터는 URL, HTTP 메서드, 상태 코드, 응답 형식만 담당하고, 실제 계산·저장·AI 호출은 서비스가 합니다."

**폴더 구조**
```
backend/
├ main.py              앱 생성, CORS, 라우터 등록, 전역 예외 처리
├ app/config.py        환경 변수 읽기 (키는 여기서만)
├ app/db.py            Firestore 연결 (키 없으면 메모리 저장소)
├ app/schemas.py       Pydantic 입력·응답 모델
├ app/routers/         data.py · conversations.py · chat.py · signals.py
└ app/services/        data_service · conversation_service · chat_service · tools · signal_service …
```

**④ 깊게 물으면**
- **Q. 나눠서 실제로 뭐가 좋았나요?**
  A. 같은 함수를 여러 곳에서 재사용했습니다. 예를 들어 기간 통계 함수 하나를 `GET /api/data/range` API, AI 도구 `get_price_range`, MCP 서버가 **중복 없이** 함께 씁니다. 요약 함수도 `/api/data/summary`와 채팅 프롬프트가 같은 함수입니다.
- **Q. DB 코드는 왜 따로 뺐나요?**
  A. Firestore 연결을 `db.py` 한곳에 모아서, 키가 없을 때는 같은 메서드를 가진 메모리 저장소로 바꿔 끼울 수 있게 했습니다. 덕분에 키 없이도 테스트할 수 있었습니다.
- **Q. 예상 못 한 오류가 나면요?**
  A. `main.py`의 전역 예외 처리기가 서버를 죽이지 않고 "서버 내부 오류" JSON(500)을 돌려줍니다. 프론트는 그 메시지를 화면에 보여 줍니다.

### 3-3. Pydantic으로 요청 검증을 한 이유와 방식

**③ 이렇게 말하기**
> "잘못된 값이 DB나 AI까지 가기 전에 **입구에서 막으려고** 썼습니다. 모델에 규칙을 적어 두면 FastAPI가 자동으로 검사하고, 틀리면 422 오류와 이유를 돌려줍니다."

**실제 규칙 (`backend/app/schemas.py`)**
- `DataCreate`: `date`는 날짜 형식, `value`는 **0보다 크고 1조 미만**(`gt=0, lt=1e12`), `memo`는 **200자 이하**, 앞뒤 공백 자동 제거
- `DataUpdate`: 바꿀 항목만 보내도 됨 (모두 선택), 보낸 값은 같은 규칙으로 검사
- `ChatRequest`: 질문 **1~1000자**, **공백만 있으면 거부**("메시지가 비어 있습니다")
- `Message`: role은 `user`/`assistant`만 허용(Literal), 내용 4000자 이하

**④ 깊게 물으면**
- **Q. 시연해 볼 수 있나요?**
  A. Swagger에서 `POST /api/data`에 `"value": -1`을 넣으면 422 오류가 나고, "0보다 커야 한다"는 이유가 나옵니다.
- **Q. Pydantic 말고 서버에서 따로 막는 건요?**
  A. 형식은 맞지만 **업무 규칙상 안 되는 것**은 라우터에서 막습니다. 같은 날짜를 또 추가하면 **409**, 없는 데이터를 수정하면 **404**, 수정할 항목 없이 PUT하면 **400**입니다.
- **Q. 422와 400 차이는요?**
  A. 422는 형식이 틀린 것(Pydantic이 자동으로 판단), 400·404·409는 형식은 맞지만 상황이 안 맞는 것(제가 직접 판단)입니다.
- **Q. 왜 질문 길이를 1000자로 제한했나요?**
  A. AI 비용(토큰) 때문입니다. 긴 글을 넣어 비용이 커지는 것을 막았습니다.

### 3-4. Firestore에 저장하고 CRUD로 다루는 방법

**③ 이렇게 말하기**
> "`firebase-admin` 패키지로 서비스 계정 키를 써서 연결했고, `data`와 `conversations` 두 컬렉션에 문서로 저장합니다. 추가·조회·수정·삭제를 각각 add, stream, update, delete로 처리합니다."

**컬렉션 구조**
```
data/{자동ID}           date, value, memo, created_at, updated_at
conversations/{자동ID}  title, messages[{role, content, tools_used}], created_at, updated_at
alerts/state           (추가) 마지막 위험 단계
alerts/{자동ID}         (추가) 디스코드로 보낸 기록
```

**④ 깊게 물으면**
- **Q. 문서 ID는 어떻게 정해지나요?**
  A. Firestore가 자동으로 만듭니다. 날짜는 필드로 저장하고, 같은 날짜 중복은 서버가 확인해서 409로 막습니다.
- **Q. 키는 어디에 있나요?**
  A. 로컬은 `serviceAccountKey.json` 파일 경로(`FIREBASE_SERVICE_ACCOUNT_PATH`), 배포는 키 JSON 전체를 Render 환경 변수 `FIREBASE_SERVICE_ACCOUNT_JSON`에 넣었습니다. 키 파일은 `.gitignore`로 GitHub에 올라가지 않습니다.
- **Q. 대화는 어떻게 저장하나요?**
  A. 채팅할 때마다 질문과 답변 두 메시지를 `messages` 배열에 이어 붙이고 `updated_at`을 갱신합니다. 제목은 첫 질문 앞 30자로 자동으로 만듭니다.
- **Q. 키가 없으면 어떻게 되나요?**
  A. 메모리 저장소로 실행되고, 화면에 "서버 연결됨 (임시 저장소)"라고 표시됩니다. 서버를 끄면 사라지는 개발용입니다.

### 3-5. 컨텍스트 주입의 원리 ★ 핵심

**③ 이렇게 말하기**
> "AI는 제 데이터를 모르니까, **질문할 때마다** 서버가 최신 요약을 계산해서 **시스템 프롬프트 맨 앞에** 넣어 줍니다. 시스템 프롬프트는 AI에게 주는 '역할과 배경 설명서'라서, AI는 그 안의 숫자를 근거로 답합니다. 이게 컨텍스트 주입입니다."

**POST /api/chat 동작 순서 (과제 문서와 똑같이)**
1. **데이터 요약 조회** — `build_summary()` (`/api/data/summary`와 같은 함수)
2. **요약을 시스템 프롬프트에 삽입** — 과제 예시 형식 그대로: 데이터 기간 / 총 레코드 / 주요 지표 / 최근 트렌드 + 오늘의 위험 단계
3. **GPT API 호출** — 이전 대화 최대 10개와 함께. 필요하면 도구 호출(최대 3회)
4. **대화 자동 저장** — 질문·답변을 `conversations`에 저장, 어떤 도구를 썼는지도 기록

**④ 깊게 물으면**
- **Q. 왜 400개 원본을 다 넣지 않고 요약만 넣나요?**
  A. 첫째 **비용**입니다. 원본을 다 넣으면 토큰이 많이 듭니다. 둘째 **정확도**입니다. 핵심 숫자만 주면 AI가 엉뚱한 숫자를 덜 고릅니다. 요약으로 부족한 특정 기간은 도구로 그 부분만 가져옵니다.
- **Q. AI가 숫자를 지어내지 않게 어떻게 했나요?**
  A. 프롬프트 규칙에 "요약이나 도구 결과에 있는 숫자만 쓴다, 없으면 '저장된 데이터에는 없어요'라고 말한다"를 넣었습니다. 답변 예시도 두 개 넣어서, 결론(숫자)을 먼저 말하고 비교 기준을 붙이게 했습니다.
- **Q. 이전 대화는 어떻게 기억하나요?**
  A. 대화 id가 있으면 저장된 메시지 중 최근 10개만 같이 보냅니다. 전부 보내면 비용이 커져서 10개로 제한했습니다.
- **Q. 프롬프트는 어디서 볼 수 있나요?**
  A. `backend/app/services/chat_service.py`의 `SYSTEM_TEMPLATE`입니다.
- **Q. 과제는 GPT인데 Gemini를 썼네요?** ★ 꼭 나옴
  A. 코드는 과제대로 `openai` 패키지와 Chat Completions 방식을 그대로 씁니다. OpenAI 키는 선불 충전이 필요해서, **Gemini가 제공하는 OpenAI 호환 주소**로 연결만 바꿨습니다. 환경 변수 3개(`OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`)만 바꾸면 **코드 수정 없이 GPT(gpt-4o-mini)로 동작**합니다. 컨텍스트 주입, 도구 호출, 저장 흐름은 똑같습니다.
- **Q. max_tokens는 얼마예요?**
  A. GPT라면 500으로 충분하지만, Gemini 2.5는 '생각하는 과정'도 토큰에 포함돼서 답이 잘려 1500으로 올렸습니다. 이것도 시행착오로 기록했습니다.

### 3-6. 배포 환경에서 CORS·환경 변수·키 관리가 필요한 이유

**③ 이렇게 말하기**
> "프론트(Vercel)와 백엔드(Render)는 주소가 달라서 브라우저가 기본으로 요청을 막습니다. 그래서 CORS로 **Vercel 주소만 허용**했습니다. 그리고 API 키와 Firebase 키는 GitHub에 올라가면 누구나 쓸 수 있어서, 코드가 아니라 **환경 변수**에만 넣었습니다."

**④ 깊게 물으면**
- **Q. CORS가 정확히 뭔가요?**
  A. 브라우저의 보안 규칙입니다. A 사이트의 화면이 B 주소의 API를 부를 때, B 서버가 "A는 허락한다"고 응답해야 브라우저가 결과를 넘겨줍니다. 우리 서버는 `ALLOWED_ORIGINS`에 적힌 Vercel 주소와 로컬 주소만 허락합니다.
- **Q. `*`(전체 허용)로 하면 안 되나요?**
  A. 편하지만 아무 사이트나 우리 API를 부를 수 있게 됩니다. 그래서 필요한 주소만 적었습니다. (코드상 `*`를 넣으면 자격 증명 허용은 자동으로 끄게 했습니다.)
- **Q. 주소 끝에 `/`를 붙이면요?**
  A. 브라우저가 보내는 Origin에는 끝 `/`가 없어서 일치하지 않습니다. 그래서 `/` 없이 넣었습니다.
- **Q. 환경 변수 목록은요?**
  A. 백엔드(Render): `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`, `OPENAI_MAX_TOKENS`, `FIREBASE_SERVICE_ACCOUNT_JSON`, `ALLOWED_ORIGINS`, `PYTHON_VERSION`. 프론트(Vercel): `API_BASE_URL`. README 10장에 표로 정리했습니다.
- **Q. 키가 노출된 적 있나요?** (솔직하게)
  A. 작업 중 화면 캡처에 키가 보인 적이 있어서, **즉시 그 키를 삭제하고 새로 발급**했습니다. 그 뒤로 키는 `.env`와 배포 환경 변수에만 두고, 캡처 전에 키가 보이는지 확인합니다.
- **Q. 프론트에서 API 주소는 어떻게 바꾸나요?**
  A. Vercel 빌드 때 `build.js`가 환경 변수 `API_BASE_URL` 값으로 `config.js`를 만들고, 화면은 그 값을 읽어서 요청합니다. 코드에 주소를 박아 두지 않았습니다.

### 4-5. 데이터 API 5개 (CRUD 4 + summary 1)

| 과제 | 우리 | 성공 코드 | 실패 처리 |
|---|---|---|---|
| POST /api/data | 추가 | 201 | 같은 날짜 409, 형식 오류 422 |
| GET /api/data | 목록 (날짜순, `limit`·`start`·`end` 선택) | 200 | — |
| PUT /api/data/{id} | 바꿀 항목만 수정 | 200 | 없음 404, 빈 수정 400, 날짜 중복 409 |

| GET /api/data/summary | 요약 (프롬프트 주입용) | 200 | 데이터 없으면 "데이터 없음" 요약 |

### 4-6. 대화 기록 API + "불러오기" UX

| 과제 | 우리 |
|---|---|
| POST /api/conversations | 대화 저장 (201) |
| GET /api/conversations | 목록 — **messages는 빼고** 제목·메시지 수·시각만, 최근 수정 순 |
| DELETE /api/conversations/{id} | 삭제 (204, 없으면 404) |
| 불러오기 (A) 또는 (B) | **(A) 방식**: `GET /api/conversations/{id}`가 전체 messages를 돌려줌 |

- **Q. 왜 (A)를 골랐나요?** A. 목록에 모든 메시지를 넣으면 대화가 쌓일수록 목록이 무거워집니다. 목록은 가볍게, 실제로 누른 대화만 전체를 받는 게 효율적이라서 (A)를 골랐습니다. README와 Swagger 설명에도 "목록은 messages 미포함"이라고 명시했습니다.

## 5장. 보너스 과제

### 보너스 ① AI 도구 호출(Function Calling) + MCP

**③ 이렇게 말하기**
> "AI에게 내부 기능 6개를 '도구'로 주고, 도구 설명을 읽고 **필요할 때만 스스로** 부르게 했습니다. 같은 도구를 MCP 서버로도 열어서 Claude 데스크톱에서 호출되는 것까지 확인했습니다."

**도구 6개와 호출 근거**

| 도구 | 언제 부르나 |
|---|---|
| `get_price_range(start, end)` | 날짜가 정해진 질문 — "3월 가격은?" |
| `get_statistics()` | "몇 번 올랐어?", "가장 크게 떨어진 구간" |
| `get_data_summary()` | 대화가 길어져 최신 요약 재확인 |
| `get_market_signals()` | "지금 팔까?", "위험해?" |
| `get_recent_news(query)` | "왜 떨어져?" 시장 분위기 근거 |
| `list_conversations()` | "지난번에 뭐 물어봤지?" |

**호출 흐름**
```
질문 → AI가 도구 설명을 보고 "도구 필요" 판단 → 도구 이름+인자(JSON) 반환
→ 서버가 실제 함수 실행 → 결과를 AI에게 다시 전달 → AI가 최종 답변 (최대 3회 반복)
→ 답변 아래 🔧 "기간 데이터 조회"처럼 표시 + 대화 기록에 tools_used 저장
```

**④ 깊게 물으면**
- **Q. AI가 도구를 고르는 기준은요?** A. 도구마다 적어 둔 설명(description)입니다. "날짜가 정해진 질문에 쓴다"처럼 적어 두면 AI가 질문과 비교해 고릅니다(`tool_choice: auto`). 요약만으로 답할 수 있으면 부르지 않습니다.
- **Q. 실제 예시는요?** A. "올해 3월 가격 흐름은?"에 AI가 `get_price_range(2026-03-01, 2026-03-31)`를 불러서 "9,590만 원에서 1억 327만 원으로 7.69% 상승, 3월 16일 최고"라고 답했습니다. 화면에 🔧 기간 데이터 조회가 표시됩니다.
- **Q. 잘못된 인자가 오면요?** A. 오류 내용을 AI에게 그대로 돌려줘서 스스로 고치게 했습니다.
- **Q. 왜 3회로 제한했나요?** A. AI가 도구를 계속 부르면 비용과 시간이 끝없이 늘어날 수 있어서입니다.
- **Q. MCP가 뭔가요?** A. AI 프로그램(Claude 데스크톱 등)이 외부 도구를 쓰게 해 주는 표준 연결 방식입니다. 제 `mcp_server/server.py`가 배포된 API를 호출하고, Claude 앱 설정 파일에 이 서버를 등록했습니다. 실제로 Claude에서 요약 조회와 기간 시세 조회가 성공했고, 발표 자료의 400일 데이터도 이 경로로 받았습니다.
- **Q. GPT Actions가 아니라 MCP를 고른 이유?** A. GPT Actions는 유료 ChatGPT 계정이 필요하고, MCP는 무료 Claude 데스크톱에서 바로 검증할 수 있었습니다.

- **디스코드 알림**: 매일 09:05 GitHub Actions → 서버가 위험 단계 계산·메시지 생성 → GitHub가 웹훅으로 전송, @everyone으로 알림. '주의' 이상으로 오를 때만 울림
- **Q. 예측이 맞나요?** A. 맞다고 하지 않습니다. 그래서 적중률을 공개했고, 단정하지 말라는 규칙과 "투자 판단은 본인 책임" 문구를 모든 신호에 붙였습니다.
- **Q. 화면 숫자가 발표 자료와 조금 달라요.** A. 발표 자료는 10월 7일까지 400일 기준이고, 서버는 매일 하루치를 추가해 다시 계산하기 때문에 적중률·횟수가 조금씩 바뀝니다. 엑셀 검증표로 같은 계산을 직접 따라가 볼 수 있습니다.
- **Q. 50.4%면 평소(48.5%)보다 높은 거 아닌가요?** A. 48.5%는 '오른다'의 기준이라 매도와 비교하면 안 됩니다. 매도는 그냥 '내린다'고 찍은 51.5%와 비교해야 하고, 그러면 비슷하거나 조금 낮습니다. 그래서 방향 예측이 아니라 '위험 신호'라고 부르고, 신호 뒤 7일 평균이 평소보다 나빴다는 점(−0.29% vs −0.21%)과 1월 말 −27.7% 하락 전 경고 사례를 근거로 듭니다.

## 8장. 결과 예시와 비교

- **요약 API 응답 예시** (`period`, `count`, `metrics`, `trend`) → 우리 `/api/data/summary`가 같은 키를 그대로 씁니다. 차이점은 `metrics`에 total 대신 최근 값·최고/최저 날짜·변동성 등 **비트코인에 맞는 지표**를 넣은 것입니다.
  - **Q. 예시엔 total(합계)이 있는데요?** A. 매출은 합계가 의미 있지만, 가격은 합계가 의미가 없어서 평균·최고·최저·변화율로 바꿨습니다.
- **시스템 프롬프트 예시** → 우리 프롬프트의 첫 부분이 예시와 같은 구조입니다(기간·레코드·지표·트렌드 + "위 데이터를 기반으로 맞춤형 답변").
- **대화 예시** "이번 달 실적이 어때?" / "가장 좋았던 때는?" → 우리 비서도 같은 유형에 답합니다.
  - "이번 달 흐름 어때?" → "이번 달 평균은 1억 1,545만 원으로 전체 월평균보다 3.8% 낮은 수준이에요…"
  - "가장 비쌌던 때는?" → "2025년 10월 8일에 1억 7,801만 원으로 가장 높았어요."

## 시연 순서 (5분, 이대로 하면 요구 사항이 모두 보입니다)

1. **사이트 열기** → 맨 위 경보판 "안전", 요약 카드(기간·개수·트렌드) 보여 주기 *(요약 표시)*
2. **채팅** "이번 달 흐름 어때?" → 로딩 점 → 숫자로 답변 *(컨텍스트 주입 + 로딩)*
3. **채팅** "올해 3월 가격 흐름은?" → 🔧 기간 데이터 조회 *(보너스 ① 도구 호출)*
4. **데이터 관리**에서 한 줄 추가 → 목록·요약 갱신 → 다시 삭제 *(CRUD)*
5. **대화 기록**에서 이전 대화 클릭 → 메시지 재표시 *(불러오기)*
6. **그래프** 기간 바꾸기, 🌙 다크 모드, CSV 내보내기 *(보너스 ②)*
7. **Swagger**(/docs)에서 `GET /api/data/summary` 실행 *(문서화)*
8. 시간이 남으면 **디스코드** 연결 완료 메시지 보여 주기 *(추가 기능)*
